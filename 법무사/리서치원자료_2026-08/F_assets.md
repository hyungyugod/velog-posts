### 1-3. 정확한 계약 3종 (이식 시 절대 훼손 금지)

#### (A) QUESTIONS 필드 계약 v2 — 문항 1개
```js
{ type, cat, q, opts, answer, expl, src, conceptKey }      // 필수 8필드
+ retryOf                                                   // 재도전 문항만
+ calc: { expr, expected }                                  // 계산형만 (JS 평가 가능 문자열)
```
- `type` ∈ {일반, 조합, 계산, 사례, OX} — **쿼터 고정**: 일반 20 / 조합 7 / 계산 4(최소 2) / 사례 4 / OX 5, `일반+계산=24` 불변
- `answer` = opts 인덱스. 사전 배정 수열(0~3 각 8회 + 3개 추가 = 9·9·9·8), 같은 값 3연속 금지
- `cat` = 과목명. **QUESTIONS 배열에서 같은 과목은 연속 배치**(렌더러가 `▍과목` 섹션 헤더를 cat 전환으로 만든다)
- `conceptKey` 형식 = `"과목 소제목-요지"` 짧게 (예: `"부동산세법 2-5 취득시기"`). **재도전은 듀 큐 값을 한 글자도 안 바꾸고 복사** — 원장 매칭의 유일한 키
- `src` = `"YYYY-MM-DD 과목 소제목"`, 재도전은 끝에 `(재도전)`, 장기복습은 `(장기복습·N일전)`
- 문자열 안에 `"`·백틱 금지 (배열이 `eval`로 검증되기 때문)

#### (B) 채점 결과 payload 스키마 v2 — `buildPayload()` 출력
```js
{ schemaVersion: 2, subject: "공인중개사", date, quizId, score, total, wrongCount,
  results: [ { id: `${date}-q${n}`, cat, type, q, options, myAnswer(텍스트), correct(텍스트),
               expl, src, conceptKey, retryOf|null, correctAnswered: bool, calc? } ],
  wrong:   [ { id, cat, type, q, options, myAnswer, correct, expl, src } ],   // v1 하위호환
  generatedAt }
```
- **v2의 핵심 = `correctAnswered`** — 맞힌 것도 기록하기 때문에 "재도전 정답"이 관측되고, 그래야 졸업이 굴러간다(v1은 오답만 기록 → 졸업 불가)
- `conceptKey` 누락 시 폴백: `conceptFromSrc(src)` = 날짜 접두 제거 + `(재도전)` 접미 제거
- 재도전 판정: `item.retryOf || /\(재도전\)/.test(src) || q.includes("🔁")` — **세 신호 중 하나만 있어도 재도전**
- 다운로드 파일명 `공인중개사_오답_{QUIZ_DATE}.json` ↔ 수거 글롭 `공인중개사_*오답_*.json` (이름이 어긋나면 루프가 조용히 끊긴다)

#### (C) 원장 스키마 (ledgerSchema 3) — 현재 실측치
최상위: `ledgerSchema:3 · generatedAt · fsrsMeta · sourceFiles 40 · v2Files 9 · submissions 40 · avgScore 33.0 · avgTotal 36 · perfectRuns 4 · totalWrongItems 100 · uniqueConcepts 99 · dateRange ["2026-06-02","2026-08-14"] · statusCounts{상습 3·재도전중 82·졸업후보 7·졸업 7} · fsrsFallbacks 0 · subjectWeakness{6과목} · dueQueue(91) · ledger(99)`

```jsonc
// ledger[] — 개념 1개 (18필드)
{ conceptKey, aliases[], subject, concept, status, timesWrong, retryMissed, consecutiveCorrect,
  firstWrong, lastWrong, lastCorrect, lastResult, lastDp, nextReviewDate, dates[],
  samples[{date,type,q,myAnswer,correct,expl}],
  fsrs:{stability,difficulty,due,state,reps,lapses,retrievability}, fsrsFallback }

// dueQueue[] — 소비자(퀴즈 생성기) 계약 (10필드)
{ conceptKey, subject, status, timesWrong, retryMissed, consecutiveCorrect,
  lastWrong, nextReviewDate, retrievability, stability }
```

**상태머신 (v2에서 한 글자도 안 바뀐 규칙):**
```
오답 발생              → consecutiveCorrect = 0   (재도전 문항이었으면 retryMissed += 1)
재도전 정답            → consecutiveCorrect += 1
consecutiveCorrect = 2 → 졸업후보
consecutiveCorrect ≥ 3 → 졸업 (듀 큐 제외, 시험 전 총복습에는 포함)
미졸업 & (timesWrong ≥ 2 or retryMissed ≥ 1) → 상습 (출제 최우선)
```
**dueQueue 선정·정렬:** `status ≠ 졸업 AND nextReviewDate ≤ 오늘` → 정렬 `(상태우선순위 상습0/재도전중1/졸업후보2 → retrievability 오름차순 → nextReviewDate → conceptKey)`. 즉 **같은 상습이면 가장 많이 잊은 것부터** 올라온다.

**FSRS 설정:** py-fsrs 6.3.2 벤더링, `desired_retention 0.9` / `maximum_interval 60`(2026-10-31 시험 대비 상한) / `enable_fuzzing False`(멱등) / `learning_steps=() relearning_steps=()`(하루 단위 시스템) / 개인 최적화 파라미터 없음 / **평가 매핑 `wrong=Again, retryCorrect=Good`(이진)**. 실패 개념은 사다리 `[3,7,16,35]`일로 폴백.

**운영 불변식:** 비파괴(어떤 파일도 삭제·이동 안 함) · 멱등(매번 전체 재생성) · **무음실패 불가(원천 0건 → exit 2, FSRS 로드 실패 → exit 3)** · 과목 별칭 정규화(`민법총칙/물권법/계약법 → 민법`)는 subject에만 적용하고 **conceptKey는 절대 건드리지 않는다.**

## 3. 법무사 특수 요구로 인한 격차 — 현행 스택이 못 하는 것

### 3-1. 🔴 2차 논술 훈련 7단위 — 대응 부품 **0개**

15호 §2가 이미 규격을 확정해 놨다(입력 프롬프트 형식 + 출력 양식 + 채점 규칙 + 순환 매핑까지):

| 단위 | 내용 | 소요/슬롯 | 현행 스택 대응 |
|---|---|---|---|
| 1 | 목차 인출 | 5분 / 자투리 / 타이핑 | **없음** |
| 2 | 첨부서면 인출 (+제공근거 1줄) | 5분 / 자투리 | **없음** |
| 3 | 청구취지 한 줄 쓰기 (4대 유형 로테이션) | 5분 / 자투리 | 로테이션 로직만 P7 유사 |
| 4 | 공식 역인출 | 3분 / 자투리 | **없음** (대표 지표인데도) |
| 5 | 유형 식별 (A~E형) | 3분 / 자투리 | **없음** |
| 6 | 완전 서술 + 첨삭 | 30~50분 / 평일저녁 / **손글씨** | **없음** |
| 7 | 실전 모드 + 총평 | 120분 / 주말 / **손글씨** | **없음** |
| 부속 | 형·형소·민소 유지 슬롯 | 90분 / 주 1회 / 목차인출만 | **없음** |

**구조적 충돌 1개 — 이게 가장 중요하다.** 데일리퀴즈 엔진은 "AI가 문제·정답·해설을 **미리 전부 만들어** HTML에 박아 두는" 배치(batch) 구조다. 그런데 15호 §0 설계원칙 1은 **"인출이 기본값이다. AI가 먼저 쓰면 훈련이 아니라 인풋이다"**이고, 12호 모듈 B는 *"현규가 '그냥 알려줘'라고 해도 1회는 '먼저 3개만 써보세요'로 되묻는다"*를 강제한다. → **단위 1~5는 배치가 아니라 대화형 왕복이어야 하므로, HTML 문제지 파이프라인으로는 원리상 구현 불가.** 재사용 가능한 것은 "원장·듀 큐가 오늘의 훈련 소재를 공급한다"는 **소재 공급 계층뿐**이고, 실행 계층은 새로 만들어야 한다.

### 3-2. 🔴 손글씨 답안 첨삭 흐름 — 파이프라인 자체가 없다

15호 단위 6·7이 요구하는 흐름: **손글씨 촬영 이미지(또는 전사) + 소요시간 + 줄 수 + 오답로그 첨부 → 루브릭 채점 → 5단 출력**. 현행 스택에서 대응되는 것이 하나도 없다.

- 채점 주체가 **JS 함수(`buildPayload`)가 아니라 LLM**이다 → 결정론적 pass/fail 게이트가 성립하지 않는다(하네스 §4의 정면 이슈)
- 결과를 담을 **payload 생성 UI가 없다** → 수거 파이프라인의 입력이 만들어지지 않는다
- 15호 §5-2가 출력 구조를 5단으로 고정: `1) 루브릭 점수표 → 2) 감점 사유 → 3) 원리→공식→체화(딱 1개) → 4) 다음 답안에서 고칠 것 딱 1개 → 5) 오답로그 기록줄(복사용 1줄)`
- **5)의 "복사해 붙일 수 있는 1줄"이 사실상 수동 `_inbox`다** — 자동 수거로 승격시킬 여지가 여기 있다

### 3-3. 🔴 채점 축이 다르다 — 원장 스키마 v4가 필요

공인중개사 원장의 축은 `conceptKey`(무엇을 틀렸나) 하나다. 법무사 2차는 **`감점코드`(어떻게 틀렸나)** 축이 하나 더 붙는다.

**반복 판정 규칙(15호 §5-3) = 원장 상태머신의 법무사판:**

| 조건 | 행동 | 공인중개사 대응 |

- **유형 쿼터가 안 맞는다**: 13호 정정 #7 — 확인된 법무사 1차 형식은 **판례지문형(압도적), ㄱㄴㄷ 조합형, 옳은 것 고르기**이고 개수형은 미확인. 반면 현행 쿼터의 **계산 4문항은 법무사 1차에 대응물이 거의 없다**(민법 199지문 중 181지문이 판례 — 13호 §3). → `type` 값 세트를 `{판례지문, 조합, 사례, OX, 일반}`으로 교체하고 `calc` 검산 단언은 제거
- `cat` 필드가 2층 구조를 못 담는다(교시/시험과목/분야). 과락은 **시험과목(제1~4과목) 단위 40점**이므로 집계 축이 하나 더 필요

### 3-7. 🟡 FSRS 파라미터 — 상수 3개가 공인중개사에 결박돼 있다

| 파라미터 | 현재값 | 근거 | 법무사에서 문제 |
|---|---|---|---|
| `maximum_interval` | **60일** | *"시험(2026-10-31) 대비, 60일 넘겨 밀지 않는다"* | 준비기간이 **14개월**(2026-09~2027-10). 초반엔 60일 상한이 과도하게 촘촘해 듀 큐 적체를 스스로 만든다. **1차(2027-08)·2차(2027-10) 이중 D-day** 처리 필요 |
| `desired_retention` | 0.9 | 목표 회상률 | 1차(재인)는 0.9 타당. **2차(회상)는 더 높게** 잡아야 한다는 논거가 있으나 검증 필요 |
| `ratingMap` | `wrong=Again, retryCorrect=Good` | 이진 정오 | 논술 루브릭은 **0~100 연속값** → Again/Hard/Good/Easy 4단 매핑 규칙이 **미정의**. 예: 논-② 결론 오류 = Again, 포섭 추상적 = Hard 등 |
| 개인 파라미터 | 없음(FSRS-6 기본 21개) | *"리뷰 로그 부족"* | 40회 제출분은 도메인이 달라 이월 불가. **법무사에서도 처음부터 다시 쌓아야** 한다 |
| 폴백 사다리 | `[3,7,16,35]` | v2 유산 | 유지 가능 |
| `DUE_BACKLOG_WARN` | 100 | 적체 경고 | 현재 **91 — 경고선 코앞**. 8과목·13분야로 늘면 훨씬 빨리 넘는다. 임계값 재설정 필요 |

### 3-8. 🟡 공식카드 파이프라인(16호) — 규격은 완비, 구현 0

이미 정의된 규격(그대로 쓰면 됨):
- 파일명 `YYYY-MM-DD-법무사-[과목코드]-[주제]-[상태].md`, 과목코드 13종, **상태 태그 4종 `초안 / 검증 / 발행 / 비공개`**
- 표준 서식 7블록: `📐 공식 / ❓ 판별 질문 / 💡 원리 한 줄 / 🔗 기억 고리 / 📌 출처 / 🔄 다음 등장` + 메타(과목·유형·상태·생성일·**마지막 역인출**)
- **2축 매트릭스**(시험 배점 × 일반인 접점) — ②사분면(배점 高·접점 低: 형·형소·민소·상업등기 = 2차 400점 중 250점)은 **발행 가치 0이어도 비공개 태그로 반드시 만든다.** 경보 규칙: *"주간 카드 생산에서 ② 비중이 3주 연속 20% 미만이면 발행이 공부를 왜곡하고 있다는 신호"*
- 승격 기준: **같은 계보 3~5장 = 포스트 1편**(카드 1장 = 1편 금지), 묶음 전원 `검증` 이상, 일반인 상황 1개로 열리지 않으면 비공개
- 카드 → 카드뉴스 5장 매핑(판별질문→커버 / 원리→2장 / 공식→3장 / 예외→4장 / 기억고리+면책→5장)
- 주간 루틴: 평일 카드 3~5장 초안 → 자투리 역인출 → 토 묶음 검증 → 일 발행 + 주간 지표 갱신

**미구현:** 상태 태그 전이 자동화, `마지막 역인출` 필드 갱신, ②사분면 비중 3주 집계, `(원문 확인 필요)` 잔존 스캔, 카드 50/100장 돌파 트리거. **전부 공인중개사 스택의 집계·검증 관용구로 만들 수 있는 것들이다.**

### 3-9. 🟡 상대평가 보정 — AI가 원리상 못 하는 것

15호 §1의 자인(그대로): *"이 AI의 루브릭 점수는 **절대 기준**이다. … '70점짜리 답안'이 합격권인지는 **모의고사 석차와 학원 첨삭**만 답할 수 있다."* → **박문각 2·3순환 모의고사 석차 병행이 시스템 요구사항이다.** 원장 설계 시 "외부 석차" 컬럼을 처음부터 비워 두고 사람이 채우게 만드는 편이 낫다(하네스 §4 "최종 검증자는 반드시 사람"의 실장).

## 4. 충돌·주의 지점

### 4-1. 🔴 월요일 수거 작업이 두 시험 원장을 혼동하는 시나리오 — **실재한다**

수거 스킬과 빌더에 **공인중개사가 하드코딩**돼 있다:
- 스킬 §0: `BASE=$ROOT/공인중개사/claude_ox_오답`, 중복 가드 `$BASE/{오늘날짜}-claude_oxquize.md`
- 스킬 §1: `find <마운트> -name '공인중개사_오답_*.json'`
- 스킬 §3: 기대치 검증 대상이 `$ROOT/공인중개사/데일리퀴즈` 의 `20*.html`
- 빌더: `RESULT_GLOB = "공인중개사_*오답_*.json"`

**분기 3개와 그 결과:**

| 선택 | 결과 |
|---|---|
| ⓐ 법무사 결과 파일을 `법무사1차_오답_*.json`으로 낸다 | 현행 스킬이 **조용히 무시**. exit 2도 안 난다(공인중개사분이 0건이 아니므로) → **무음 실패 유형 3번째 재발** |
| ⓑ 파일명을 `공인중개사_오답_*`로 맞춘다 | 두 시험이 **한 원장에 섞인다**. `conceptKey`는 문자열 매칭이라 `"민법 …"`이 어느 시험의 민법인지 구분 불가 — 합격수기 보고서 §7: *"중개사 민법은 법무사 민법의 1/10"*, 강택구는 *"사실상 노베이스"*로 규정. **개념 공간이 다르므로 섞이면 FSRS 추정이 오염된다** |
| ⓒ **스킬·빌더·원장을 시험별로 완전 분리**(권장) | taskId·BASE·글롭·원장 파일이 전부 별개. 유일한 비용은 스킬 2벌 유지(드리프트 위험 → §4-5) |

**추가 함정:** 중복 가드가 **날짜 파일명 기준**이다. 두 시험이 같은 폴더 규칙을 공유하면 **먼저 생성된 쪽이 나중 쪽을 차단**한다(“오늘 문제지는 이미 생성되어 있다”고만 알리고 종료).

### 4-2. 🟠 요일 슬롯 포화 — 월요일에 이미 3건

현재 월요일: 11:01 오답 수거 / 20:08 일기 동기화 / 21:05 지식 인덱스. 여기에 법무사 수거를 더하면 4건.
- 15호 §6-3은 **주간 지표 갱신을 "매주 일요일"**로 지정 → 법무사 주간 집계는 **일요일**이 정합적이다(주말 롱블록 단위 7 직후 = 데이터가 막 생긴 시점)
- 단 일요일 11:00에 `weekend-daily-quiz`가 이미 돈다 → 시간대를 밤(예: 21:00)으로 분리
- 하네스 §5의 **"읽기는 병렬, 쓰기는 직렬"** — 두 수거 작업이 같은 시각에 velog-posts에 쓰면 조정 장치가 없다. **시각을 겹치지 않게 두는 것이 유일한 lock이다**

### 4-3. 🔴 2026-09~10 3중 부하 — 지금 법무사 스케줄을 켜면 안 된다

13호 §6 표: `2026.9~10 = 중개사 제37회 + 법무사 1차 기본이론 + 2차 입문강의 → **3중**`. 15호 §8-2 구간 ①이 이미 규정: *"선택적 수강기. 중개사 제37회(10/31)까지 법무사:중개사 = 2:5. **민법·부동산등기법만 선행**"*, 주력 훈련 단위는 **단위 4(역인출)만**.
- `velog-posts/법무사/README.md`도 **"11/2 본격 가동"**으로 자기 선언 완료
- 마스터플랜 §1: *"가이드라인을 다듬는 시간은 자산이 아니라 비용이다"* + §5 P4 규율(지금 실행 2개 / 나머지는 게이트 뒤)
- → **9~10월에 할 일은 "폴더·스키마·파일명 규칙 확정"까지이고, 스케줄 태스크 신규 등록·엔진 이식은 11월 게이트 뒤**가 원칙 정합적이다

### 4-4. 🟠 관측성이 성립하지 않는 훈련 형태

하네스 §9 표준 장치 4종은 **"산출물 파일이 남는다"**를 전제한다(하트비트 = 파일 존재, 기대치 검증 = 생성 N vs 도착 N).
법무사 단위 1~5는 **대화로 끝나고 파일이 안 남는다** → 하트비트도 기대치 검증도 원리상 불가.
**처방 후보:** 훈련 세션 종료 시 `오답노트/`에 1줄 append(15호 §5-2의 5번 출력이 이미 그 형태)를 **강제**하고, 그 파일의 라인 수 증가를 하트비트로 삼는다. 즉 **"AI 출력의 마지막 한 줄"을 파이프라인 입력으로 승격.**

### 4-6. 🟠 신뢰 경계(trifecta) — 법무사에서 위험 축이 하나 늘어난다

| 파이프라인 | ①비공개 접근 | ②신뢰불가 콘텐츠 | ③외부 전송·게시 | 판정 |
|---|---|---|---|---|
| 공인중개사 오답 수거 | 로컬 JSON | 낮음(자기 생성물) | 로컬 쓰기 | 🟢 |
| 법무사 오답로그 | **감점·약점 날것** | 낮음 | 로컬 쓰기 | 🟢 |
| **법무사 공식카드 → velog 발행** | 오답노트가 **같은 저장소 트리**에 있음 | 조문·판례 조회 | **공개 게시** | 🟠 → 자동 발행을 붙이면 🔴 |

16호가 이미 이중 안전장치를 설계했다: **폴더 분리**(`오답노트/`는 발행 대상 아님) + **파일명 상태 태그**. 하지만 *"velog-posts는 발행용 폴더다. 오답 기록이 섞여 들어가면 공개 사고가 난다"*가 곧 **①과 ③이 한 저장소에 산다**는 뜻이다. 하네스 §8 Rule of Two대로 **셋 중 둘까지** — 발행 단계에 사람 승인 게이트를 남기고, **발행 자동화는 P4 trifecta 체크를 통과하기 전엔 붙이지 않는다.**

### 4-7. 🟢 계승해야 할 금지 규칙 (위반 시 실사고 재발)

- **Self-OS vault git에 어떤 쓰기 명령도 금지** (add/commit/reset/checkout/branch/stash/worktree) — 샌드박스 마운트 경유 git 쓰기가 index 손상(NUL)·락 잔류의 원인이었음. 예외는 velog-posts **읽기 전용 `git log`만**
- **velog-posts는 독립 저장소** — 커밋·푸시는 사람이 Windows에서 직접
- 템플릿의 **`buildPayload`/`downloadResult`/클립보드 폴백/👁 소거 UI 수정 절대 금지** (채점·저장의 단일 원천)
- **`conceptKey`는 변형 금지** (원장 매칭 키)

### 5-1. 마스터플랜 v1.0 (이 저장소의 정점 문서)

1. **북극성**: *"다음 모델이 나올 때마다 리셋되는 사람이 아니라, 배가되는 사람"*
2. **복리 자산 vs 소모품**: 마크다운·JSON 원장·스킬·evals는 이월되고, 프롬프트 강조어·모델별 우회 트릭은 삭제 대상. *"소모품을 자산으로 착각해 지키는 것"*이 진짜 잘못
3. **형식 표준(§3①)**: 평문 마크다운 + JSON 원장, **append-only·비파괴·멱등**, 로컬 파일(file over app). *"내 오답 원장의 철학이 정확히 이것 — 확신 갖고 전 데이터에 확대 적용"* → **법무사 원장도 같은 형식으로 간다**
4. **§6 상시원칙 2**: 원장류는 **LLM에게 통째 재작성 시키지 않는다**(ACE 연구: 재작성은 붕괴). 감사 리포트도 *"원장을 요약본으로 교체하고 싶은 유혹이 와도 하지 말 것"*
5. **§6 상시원칙 3**: 반복 작업은 프롬프트가 아니라 **스킬(마크다운+스크립트)로 패키징** — 모델 불문 이식
6. **§6 상시원칙 4 (Compound)**: *"이번 주 AI에게 같은 지시를 2번 이상 했나? → 했다면 지침·스킬로 승격"*
7. **evals가 왕관 보석(§3④)**: *"내 기준으로 채점하는 테스트 세트는 모델이 강해질수록 더 유용해지는 유일한 인공물."* 격차 1순위가 **evals 부재**
8. **P4 게이트 규율(§5)**: "지금 실행"과 "게이트 뒤 백로그"를 강제 분리. 새 제안은 ①분기 목표 정합 ②무엇을 줄일 것인가 ③24시간 지연 — 셋 다 통과 못 하면 보관만
9. **메타작업 중독 경고(§1)**: *"가이드라인을 다듬는 시간은 자산이 아니라 비용이다. 자산은 원장·발행물·청중·합격증뿐이다."* + *"모델 릴리즈 주간에 시스템 전면 개편 금지"* + **"구조 변경 2개 동시 금지"**
10. **수익화 0단계**: 자격 취득 전 수익화 금지. 보호 영역(창작·헬스·사람)은 줄이지 않는다

### 5-2. 하네스 공통 원칙 v2

1. **하네스 = 모델이 혼자 못 하는 것에 대한 가정을 코드·문서·절차로 인코딩한 것.** 성능은 "모델"이 아니라 **모델×하네스 쌍**의 속성(하네스 간 23.8%p 격차). **새 모델마다 한 층씩 제거해 load-bearing 재검증**
2. **도구 선택 매트릭스**: 항상 적용되는 짧은 규칙 → CLAUDE.md / 가끔 필요한 워크플로 → **스킬** / **반드시 일어나야 하는 일 → 훅**(프롬프트는 권고, 훅은 보장) / 탐색·대량 읽기 → 서브에이전트 / 세션 간 연속성 → **상태 파일 + git**
3. **컨텍스트 경제학**: *"원하는 결과의 확률을 최대화하는 최소의 고신호 토큰 집합."* 가지치기 기준 = *"이걸 지우면 실수가 생기는가? NO면 삭제."* 데이터를 사전 적재하지 말고 **식별자만 두고 JIT 로드**
4. **검증이 루프를 닫는다**: 에이전트가 직접 읽는 **pass/fail 신호**를 줘라. 게이트 4단계(프롬프트 → 완료조건 → **훅** → 검증 전담 서브에이전트). **자기 평가는 신뢰 불가**(코드든 콘텐츠든). 게이트엔 **우회 금지문 + 탈출구**("과제가 이상하면 풀지 말고 보고") 명시
5. **읽기는 병렬, 쓰기는 직렬** — 쓰기 병렬은 lock·worktree·샤딩이 있을 때만
6. **장기 실행 3종 세트**: 상태 파일(변조 금지 체크리스트는 **JSON**으로 — 모델이 MD보다 JSON을 함부로 안 고친다) / 세션 리추얼(상태 읽기 → 스모크 → **한 단위만** → 커밋 후 종료) / E2E 검증
7. **evals**: 실전 실패 사례 **20~50개로 일찍** 시작. 채점자 우선순위 코드 > LLM 판정 > 인간. **경로가 아니라 결과를 채점.** 간헐 실패는 pass@1이 아니라 **pass^k**로 잰다. 점수 말고 **transcript를 읽어라**
8. **신뢰 경계**: 실수 방어 ≠ 공격 방어. **lethal trifecta / Rule of Two(셋 중 둘까지)**. *"프롬프트 문구는 위생이지 방어가 아니다 — 진짜 방어는 능력 분리."* 무인 실행(크론)일수록 쓰기 범위를 좁힌다
9. **관측성 표준 장치 4종**(모든 스케줄 파이프라인 기본 장착): ①하트비트(산출물 파일 = 생존 신호, 결측 자동 보고) ②기대치 검증(만든 N vs 도착 N) ③**0건 = 실패(exit 2)** ④**실패의 흔적**("실패했다 + 사유 1줄" 파일은 남긴다) + 주간 회고 1줄 *"이번 주 모든 스케줄이 예정 횟수만큼 돌았나?"*

### 5-3. Self-OS 하네스 설계도

1. **검증 신호는 행동만 센다** — *"느낌상 성장" 서술 금지, 파일·발행 링크·횟수만.* 자기개발의 "빌드 성공" = **산출물이 세상에 나갔는가**
2. **실패 모드**: 루틴 증발 / **수집만 하고 발행 0** / 새 프로젝트 폭주
3. **에이전트 3종이면 충분** — 과잉 분리 금지. 병목은 생성이 아니라 **회고의 정직함과 발행의 강제**
4. **가드레일 4**: 새 프로젝트 게이트 / 보호 영역 알람(창작·운동·사람이 0이면 최상단 경고) / **수집가 함정 감지(지식 추가 대비 발행 < 3:1이면 "변환 적체" 경보)** / 자학 패턴 개입(회고를 처벌로 쓰지 않는다)
5. **안티패턴**: 5분 넘는 회고 리포트 / 에이전트가 일일 로그 대필 / 매주 목표 재설계 / **하네스 만들기가 또 하나의 회피성 프로젝트가 되는 것 — 설정은 30분, 평가는 발행 수로**

### 5-4. 이 세 문서를 법무사 설계에 대입하면 나오는 제약 5줄

1. 법무사 원장은 **JSON·append-only·멱등·exit 2**로 만든다 — 형식은 이미 결정돼 있다(선택지가 아니다)
2. 훈련 단위는 프롬프트가 아니라 **스킬로 패키징**하되, **파일이 남는 형태**로 설계해야 관측성이 성립한다
3. 새 스케줄은 **하트비트·기대치 검증·0건=실패·실패 흔적** 4종을 처음부터 달고 태어난다
4. 스킬을 만들기 전에 **실패 사례 20개짜리 회귀 세트**를 먼저 만든다(evals 격차가 마스터플랜 1순위)
5. 9~10월은 **중개사 엔진이 우선**이다 — 법무사 인프라는 11/2 게이트 뒤. 그 전에 하는 일은 "폴더·스키마·명명 규칙 확정"까지
